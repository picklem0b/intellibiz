# RFC-006: Dependency Injection

**Status:** Accepted
**Dependencies:** RFC-001
**Implemented In:** `@intellibiz/core`

---

## Problem

Service instantiation in Node.js applications is typically handled in one of two ways: global singletons imported at the top of every file, or manual constructor injection threaded through function call chains. Both approaches have compounding problems at scale.

**Global singletons** create invisible coupling between modules and make unit testing impossible without module-level mocking. When a `db` import at the top of a file connects to a real database, every test that imports that module pays the cost of that connection — even if the test has nothing to do with the database. Replacing the database adapter for a different environment (test, staging, local) requires either environment-specific code at the import site or a mocking library that intercepts module resolution.

**Manual constructor injection** solves the testability problem but creates a different one: every function in the call chain that needs a downstream service must accept it as an argument and pass it down, even if the function itself does not use the service. A route handler that calls an action that calls a utility that calls a database query must thread `db` through four levels of function signatures even though only the bottom level actually uses it.

Neither approach is appropriate for a multi-tenant business engine where services like `db` are not static — they are scoped to the current tenant and must carry that scope transparently through the entire execution chain.

---

## Motivation

The DI container in Intellibiz has a single, specific job: make the right services available to the right code at the right time, with no manual wiring and no global state.

When a developer writes `ctx.db.findOrders()`, they should not need to know that `db` is a Kysely instance wrapping a PostgreSQL pool, that it has been configured with the current tenant's `org_id`, that it will automatically append `WHERE deleted_at IS NULL` to every query, and that every query it executes is being observed by the Rust query planner. All of that is the container's responsibility.

The container also makes plugins (RFC-004) possible. A plugin that provides a new payment provider registers it in the container, and the rest of the system can use it through the same `ctx.payments` interface without knowing whether it is the built-in Stripe adapter or a third-party plugin.

---

## Proposal

Implement a DI container in `@intellibiz/core` that manages service lifecycles and injects the correct service instances into each execution context (RFC-001). The container supports three service scopes and integrates with AsyncLocalStorage so that scoped services automatically reflect the current request's tenant and user.

### Service Scopes

| Scope | Lifecycle | Instances | Use Case |
|-------|-----------|-----------|----------|
| `singleton` | Application lifetime | 1 per app | Database pool, config, ledger writer |
| `scoped` | Request / action lifetime | 1 per ALS context | Tenant-scoped db proxy, request logger |
| `transient` | Per resolution | 1 per `container.get()` call | Stateless calculators, formatters |

### Service Registration

Services are registered at boot time by the kernel and by plugins. Developers do not interact with the container directly in application code.

```typescript
import { container } from '@intellibiz/core'

// Singleton — one instance for the entire app lifetime
container.register('ledger', () => new LedgerWriter(), { scope: 'singleton' })

// Scoped — one instance per ALS context, constructed with tenant info
container.register('db', (ctx) => createTenantDb(ctx.tenantId), { scope: 'scoped' })

// Transient — new instance every time it is resolved
container.register('taxCalculator', () => new TaxCalculator(), { scope: 'transient' })
```

### Context Injection

Services are not imported. They are injected into every context object automatically by the kernel when the context is created. Developers access them via `ctx.*`:

```typescript
export const getOrders = defineAction(async (ctx) => {
  // ctx.db is a scoped Kysely proxy for ctx.tenantId
  // ctx.log is a Pino child logger with traceId, tenantId, userId
  // ctx.ledger is the singleton LedgerWriter
  const orders = await ctx.db.findOrders()
  ctx.log.info('orders.fetched', { count: orders.length })
  return orders
})
```

### Override Support

Services can be overridden by plugins or by the application's override files without modifying core packages. The last registration for a given key wins, with a conflict logged as a governance warning if two non-core registrations attempt to claim the same key.

```typescript
// intellibiz/db-override.ts — generated by the CLI when overrides.dbQueryLogic is true
import { defineDbOverride } from '@intellibiz/core'

export default defineDbOverride({
  onFindOrders: async (query, ctx) => {
    if (ctx.role === 'SuperAdmin') query.includeDeleted = true
    return query
  },
})
```

## Examples

**Accessing injected services in an action:**

```typescript
export const cancelSubscription = defineAction(async (ctx) => {
  const subscription = await ctx.db.findSubscription(ctx.data.subscriptionId)
  if (!subscription) throw new NotFoundError('SUBSCRIPTION_NOT_FOUND')

  await ctx.ledger.record('subscription.cancelled', {
    subscriptionId: subscription.id,
    userId: ctx.userId,
    reason: ctx.data.reason,
  })

  await ctx.db.updateSubscription(subscription.id, { status: 'cancelled' })
  await ctx.emit('SubscriptionCancelled', { subscriptionId: subscription.id })

  return { success: true }
})
```

**Plugin registering a custom service:**

```typescript
definePlugin({
  name: 'vatstack-tax',
  services: {
    'tax.provider': (deps) => new VatstackProvider(deps.config.vatstack),
  },
})
```

## Advantages

- **Zero import boilerplate.** Developers never import `db`, `ledger`, or `log` directly. They are always available on `ctx`.
- **Testability without mocking frameworks.** Replace any service in the container during test setup. No module-level mocking, no `jest.mock()`, no import interception.
- **Tenant scope is automatic.** The scoped `db` service is constructed with the current ALS context's `tenantId`. Developers cannot accidentally use the wrong tenant's database connection.
- **Plugin extensibility.** The container is the integration point for the plugin system. Any service can be replaced or augmented by a plugin.

---

## Disadvantages

- **Implicit dependencies.** When services come from `ctx` rather than explicit imports, it is harder to determine at a glance what a function depends on. This is the fundamental trade-off of all DI systems.
- **Boot-time only registration.** Services must be registered before the application starts. Dynamic service registration at runtime is not supported, which constrains some plugin architectures.
- **Circular dependency risk.** Service A that depends on Service B that depends on Service A is a runtime error that is not caught by TypeScript. The container must detect this at boot.

---

## Alternatives

**Option A: InversifyJS or TSyringe.**
Use an existing TypeScript DI framework. Rejected because existing frameworks are designed for class-based injection with decorators. Intellibiz's functional style and ALS-based context system require a DI container that is aware of the current execution context — something no existing framework provides out of the box.

**Option B: Explicit imports with a test-time replacement mechanism.**
Keep global imports but provide a `setService('db', mockDb)` utility for tests. Rejected because this introduces global mutable state and makes parallel test execution unreliable.

**Option C: Pass services as the first argument to every handler.**
`defineAction(async (ctx, { db, ledger, log }) => {...})`. Rejected because it makes the handler signature longer without adding type safety — the services are still injected by the framework, not the developer.

---

## Implementation Notes

- The container is initialized in `@intellibiz/core` during `app.onInit`. All singleton services are constructed at this point.
- Scoped services are lazily constructed when first accessed on a given ALS context. Subsequent accesses within the same context return the same instance.
- The kernel calls `container.createScope(ctx)` when creating each new request, action, or job context. This returns a scoped proxy object that resolves scoped services against the current context.
- TypeScript types for `ctx.db`, `ctx.ledger`, etc. are declared in `@intellibiz/types` and extended by packages and plugins via module augmentation.

---

## Future Work

- **Async service initialization.** Some services (e.g., a database pool) need to perform async work before they are ready. The container currently assumes synchronous construction. An `onReady()` hook per service is needed.
- **Service health checks.** Allow services to declare a `healthCheck()` function that the dashboard and CLI can call to verify that each service is operational.
- **Scoped service isolation in tests.** A `container.runIsolated()` utility that creates a completely isolated container scope for a single test, with no shared state between tests.
